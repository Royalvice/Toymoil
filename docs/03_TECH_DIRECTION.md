# Toymoil 技术方向

## 总原则

先建立游戏体验，再提炼框架。每次抽象都应回答一个已经在两个以上真实内容中出现的
重复问题；不能为了“看起来可扩展”而先搭建没有使用者的平台层。

## 空间模型

游戏规则运行在真实 3D 世界中。地面坐标是 X/Z，高度是 Y；物理、导航、射线和
地形不接受为镜头投影服务的全局非均匀变形。

2D Sprite 是 3D 实体的视觉表现，而不是物理本体。角色的碰撞、位置、高度和状态
由 3D 节点或规则对象负责，Sprite 负责动画、方向和可读性。

## 视觉路线

Sprite 需要相对于正式相机保持稳定正面读图。具体使用相机平面 Quad、Billboard、
自定义 Shader 或其他方案，由镜头原型决定；目标是所有地图位置都不暴露卡片侧面，
同时正确参与深度、遮挡和必要的灯光表现。

地图结构优先使用真实几何，像素细节可以使用贴图、Decal 或面向相机的 Sprite。
规则坐标与视觉偏移分开，跳跃或浮空不能靠移动贴图假装物理高度。

## 模块关系

优先使用最容易追踪的通信方式：

1. 同一职责内部使用直接方法调用。
2. 父子或明确协作者使用导出引用、构造参数或节点路径。
3. 一个对象通知少量已知观察者时使用局部 Signal。
4. 只有真实出现跨多个系统的广播需求后，才评估类型事件系统。

不提前建立全局 EventBus，因为它会隐藏发送者、接收者和生命周期关系，也更容易让
后续 Agent 在不知道影响范围的情况下添加耦合。

## 内容与数据

首个原型可以直接使用场景和简单 Resource。随着同类角色、武器或敌人增加，再把
稳定差异提取为数据。数据驱动是逐步得到的结果，不是第一天必须完成的基础设施。

## Agent-first 扩展

长期目标是让一个新内容单元具有明确输入、编辑器预览、验证规则和人工验收，而不必
修改无关系统。实现这一点应依靠小而清晰的合同、可打开的场景和局部测试，而不是
一套覆盖所有未来内容的预设框架。

## 暂不锁定

- Addon 数量和依赖图。
- Composition Root、Registry、Event 类型或状态机框架。
- 正式相机实现和 Sprite 渲染节点。
- 导航、对象池、存档、音频和 Mod 系统。

这些选择应在相应原型暴露真实约束时再作决定。
